# Снимок веток перед уборкой — 2026-08-17

Две ветки, оставшиеся после сессий 16.08. Обе удаляются локально и в origin.

## Чем этот снимок отличается от [снимка 07.08](git-branch-manifest-2026-08-07.md)

Тогда все ветки были **влиты в main**: их коммиты — предки `main`, поэтому восстановление
по SHA работает всегда, сколько бы времени ни прошло.

Здесь не так, и это важно записать честно. Эти ветки в `main` **не влиты** — их коммиты
не предки `main`. Они **эквивалентны по содержимому**: каждый коммит обеих веток
воспроизводит изменение, которое в `main` уже есть, но под другим SHA. Проверено
`git log --cherry-mark --left-right main...<ветка>` — уникальных коммитов (метка `>`)
**ноль на обеих**.

Практический вывод из этой разницы: **содержимое не теряется никогда** (оно в `main`),
а вот сами объекты коммитов после удаления ссылок становятся недостижимы и однажды
уедут в сборку мусора. То есть восстановление ИМЕННО ЭТИХ SHA имеет горизонт; восстановление
содержимого — нет, оно и так в `main`.

## Откуда взялись

Тот же класс, что записан в самом коммите точки расхождения: серверный чекаут **один
на все сессии**, `git commit` без явных путей забирает весь индекс, и работа расходится
по нескольким SHA. По каждой из трёх тем в истории теперь по два-три коммита-близнеца
с одинаковыми заголовками; два из них дошли до origin разными путями, остальные осели
на этих ветках.

Разбор столкновения, которое из этого вышло, — в merge-коммите `75c33b7`
(«Merge origin/main: the signal merge stays deleted»).

## Восстановить

```bash
git branch <имя> <sha>                    # локально
git push origin <sha>:refs/heads/<имя>    # в origin
```

Работает, пока объекты не собраны сборщиком мусора. Если SHA уже недостижим, восстанавливать
нечего и незачем: то же содержимое лежит в `main` под другими SHA — см. таблицу выше.
